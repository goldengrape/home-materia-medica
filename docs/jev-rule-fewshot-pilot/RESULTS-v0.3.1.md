## 1. 这一版真正测试什么

v0.3.1 不再测试“结构化 packet 能不能让 Jev 猜标签”。

实际 state 是一个连续 Markdown 文本：

```text
判定方法
+ 5 个自然语言说明文档式参考示例
+ 1 个自然语言待判断说明文档
```

target 没有 `organoleptic_sensory`、`traditional_functions`、`traditional_indications` 等 JSON 字段。Jev 需要从说明文档里自行识别：

- 感官线索；
- 功能方向；
- 主治 / 症候；
- 寒热方向；
- 脏腑功能群；
- 五味的“散、泄、补、收、软”等功能模式。

Question schema 只负责限定输出字段，不承担推理教学。

## 2. v0.3 #11 为什么作废

Actions #11 首次验证了“文档 + 推理规则”方向，但发现两个测试合同错误：

1. 余甘子药典归肺、胃经，rules 已经把“消食健胃 / 消化不良 / 腹胀”识别为脾胃功能群并支持脾，但 gold 却把胃简单丢掉，导致 Jev 三次正确推到“肺、脾”却被记成假阳性。
2. 紫苏子虽然传统记录为温，但本轮说明文档只有降气化痰、止咳平喘、润肠通便，缺乏足够的温性桥梁；Jev 三次偏向平，不能把这个结果简单算作模型错误。

因此 #11 只作为 design-check run，不计入正式 accuracy。

## 3. v0.3.1 修正

### 五脏功能群投影

因为最终产品只输出心、肝、脾、肺、肾：

- 胆 → 肝胆功能群 → 肝；
- 胃 → 脾胃功能群 → 脾；
- 大肠 → 肺与大肠功能群 → 肺；
- 小肠 → 心与小肠功能群 → 心；
- 膀胱 → 肾与膀胱功能群 → 肾；
- 三焦不固定映射，按具体上下焦语境判断。

这是五字段输出时的项目工作投影，不表示传统理论中六腑归经与五脏归经等同。

### 温性样本

紫苏子替换为草豆蔻。草豆蔻说明文档包含：

- 温中止呕；
- 寒湿内阻；
- 脘腹冷痛；
- 中焦脾胃功能群。

因此“温 / 辛 / 脾”的 gold 可以从文档内部完整推出。

## 7. 这次结果可以说明什么

### 可以说明

当输入说明文档满足：

1. 资料本身包含足以支持标准答案的线索；
2. rules 明确说明如何从症候 → 功能群 → 四气 / 五味 / 五脏归经；
3. few-shot 使用相同推理方法；
4. question schema 只负责限定最终结果；

Jev 可以稳定复现这套判定规则。

这支持继续采用：

```text
说明文档
+ 项目推理规则
+ few-shot
→ Jev
→ 固定 JSON 结果
```

而不需要额外概率修正函数。

### 不能说明

本轮 100% 不是“Jev 已经能自动判定所有食品四气五味归经”。

本轮说明文档是为验证推理链而整理成**reasoning-complete** 的文本：结果与文档具有明确内在一致性。它主要验证的是“给足项目认可的桥梁后，Jev 能不能照规则走完映射”。

下一阶段真正困难的问题是：

> 《居家本草》的真实 Research Dossier / 条目说明文档，是否天然包含足够、不过度引导、且可追溯的这些桥梁？

这需要用真实食品研究材料做外域测试。
